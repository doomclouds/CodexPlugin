# Workflows 0.10.0：单一结构化定义与持久执行状态机

日期：2026-10-16。状态：0.10.0 已实现、验证、推送并安装；原聊天连接仍需重载。具体边界见 [本版验证记录](0.10.0-verification.md)。用户决策：不兼容旧脚本，不保留旧执行协议，不做旧格式迁移。

## 1. 核心决定

工作流只有一种定义：经过 Schema 校验的结构化 JSON。AI 通过 MCP 创建和更新定义，用户描述需求、查看计划和运行。

定义经过规范化与校验后，成为唯一可执行流程树。执行器按这棵树调度；计划图由同一棵树生成；运行状态来自节点实例的持久状态。不存在“执行任意脚本，再从源码猜一张图”的第二套语义。

不保留 JavaScript 工作流入口、AST 推图、注释标签协议或自由脚本回退。复杂业务放在明确的 agent / command 活动中；需要作为流程展示的分支、循环和并行，必须在定义中表达。

**结构化的是编排，不是业务能力。** agent 仍通过真实 Codex worker 使用原生文件、命令、修改工具和明确授权的 MCP。任务变化生成不同定义，不为每种需求新增引擎代码。

## 2. 整体关系

~~~mermaid
flowchart LR
  A[用户描述目标] --> B[AI 通过工具生成结构化定义]
  B --> C[Schema 与权限校验]
  C --> D[冻结的可执行流程树]
  D --> E[持久执行状态机]
  D --> F[计划结构]
  E --> G[节点实例与尝试]
  G --> H[事务化状态与事件]
  H --> E
  H --> I[服务端状态投影]
  F --> I
  I --> J[面板布局与节点过程]
  E --> K[Codex 原生 worker / 命令执行器]
  K --> E
~~~

编译仅补齐默认值、解析引用、校验作用域和生成规范控制边；不能猜测定义没有声明的业务关系。编译产物与定义摘要绑定，运行中冻结。

## 3. 唯一的定义模型

### 基础活动

| 活动 | 职责 |
| --- | --- |
| agent | 让模型使用真实工具完成任务，返回经过校验的结果 |
| command | 执行定义中声明的精确 argv；权限、超时、环境、产物与副作用策略明确 |
| transform | 无 I/O 的确定性数据转换；复杂处理交给 agent 或 command |
| wait | 等待明确的宿主动作、用户决定或外部结果；等待不等于成功 |
| subflow | 调用固定版本的可复用子流程 |
| expand | 运行时生成并确认同一种结构定义的子流程 |

### 结构控制

| 结构 | 执行语义 |
| --- | --- |
| steps | 容器内按顺序执行；顺序来自结构，不来自任务数组位置 |
| choice | 多路条件与默认分支；只激活实际选中的分支 |
| parallel | 静态分支并发，必须指定汇合与失败策略 |
| map | 固定本次输入集合，按唯一 itemKey 创建实例，并限制并发 |
| repeat | 继续或退出条件、最大轮数明确；允许嵌套 |
| try / catch / finally | 异常处理与收尾属于执行结构，不靠 failure 变量模拟 |

控制流是受约束的流程树，不允许任意节点回边。循环通过 repeat 表达，跨段组合通过 subflow 表达。这使退出、错误传播、并行汇合和资源生命周期可以完整校验。

条件和数据映射使用有类型的字段引用、比较、布尔组合、算术与集合操作，不使用 eval 或任意脚本。条件不得启动任务、访问文件或调用网络。状态只接收明确的 JSON 值，拒绝循环引用、不可序列化对象和隐式类型转换。

### 定义示意

以下使用已实现的定义语法，省略具体任务的可选输出 Schema 和 Run 授权：

~~~json
{
  "schemaVersion": 1,
  "name": "update-build-verify",
  "description": "根据实际检查结果更新与构建",
  "steps": [
    {
      "id": "inspect",
      "type": "agent",
      "task": "检查原项目与执行能力，输出结构化事实"
    },
    {
      "id": "fetch",
      "type": "agent",
      "task": "获取远端并固定目标提交，报告是否有更新"
    },
    {
      "id": "has-updates",
      "type": "choice",
      "cases": [
        {
          "id": "has-updates",
          "when": {
            "op": "eq",
            "args": [{ "ref": "steps.fetch.output.changed" }, { "literal": true }]
          },
          "steps": [
            {
              "id": "update",
              "type": "agent",
              "task": "按已固定目标完成授权范围内的更新"
            }
          ]
        }
      ],
      "default": []
    },
    {
      "id": "build",
      "type": "agent",
      "task": "安装、构建并检查"
    }
  ]
}
~~~

此示意省略 Run 的 projectPath、grants 和 limits；它们属于本次执行，不写进可复用定义。输出 Schema、accept 和错误收尾按实际任务显式补充，并非全部活动的必填字段。写任务须将 agent.mode 或 command.effect 声明为 write，且 Run 允许写入。无更新分支自然汇合到 build，无需面板为特定项目补画连线。

业务步骤内部的工具调用显示在节点过程里，不自动变成主图节点。一个 command 内部可能执行复杂程序；主图承诺的是已声明的工作流边界，不宣称还原该程序内部控制流。

## 4. 定义、实例、尝试严格分开

| 对象 | 身份与用途 |
| --- | --- |
| Definition | definitionId + revision + hash；可复用的结构、参数 Schema 和任务配置 |
| Run | runId；固定项目、输入、定义快照及授权 |
| NodeInstance | instanceId + definitionNodeId + parentInstanceId；一次真实激活 |
| Loop / Map / Branch | 完整作用域路径、循环激活与轮次、itemKey、branchId |
| Attempt | attemptId；某个实例的一次执行尝试，保存真实工具上下文与结果 |
| Commit | 已确认输出、项目证据和状态提交位置，作为继续执行的依据 |

定义里一个节点可以产生很多实例。循环第 1 轮和第 2 轮、两个并行分支、两次重试不能共用“最近状态”。

下游只读取已提交的实例输出。分支读取独立的已提交 JSON 数据上下文，文件读取仍面向同一工作区视图；分支分别产生输出；汇合使用明确的输出槽位或 reducer，不允许共享可变对象或按完成先后覆盖。

格式 Schema、任务验收和业务选路分开：Schema 检查形状，任务验收判断该任务是否完成，choice 处理合法的业务结果。例如“没有新提交”可以是成功结果，不应该为了让它分支而制造一个失败节点。

## 5. 持久化与恢复从状态机继续

实现使用 node:sqlite 的 SQLite 事务存储，独立命名空间为 structured-v1；定义快照、节点实例、attempt、控制游标、事件和派发意图在同一运行状态提交中持久化。工作区与项目证据存入运行自有目录。安装要求 Node.js >= 22.15.0；SQLite 使用 WAL 和 FULL synchronous。运行与控制响应有明确体积上限，不把 UI 截断视图当成恢复权威。

执行顺序：

1. 校验输入、工具目录、项目、工作区与实际授权。
2. 持久提交实例状态、派发意图和调度令牌，再启动实际 worker。
3. 收到结果后校验格式、任务验收及相关项目证据。
4. 将确认的结果、状态变化、事件和检查点引用在同一事务提交。
5. 调度依赖这些已提交结果的后继实例。

数据库提交只能保证数据库内部的一致性，不能替代文件或远端系统的事务。派发请求已发送但创建结果未知时，不能仅因派发意图还在就重新创建有副作用 worker；需要幂等接收端或先核对实际状态。大文件先写入不可变对象并核验，再提交数据库引用。

恢复加载控制游标、已提交输出、已选分支、循环位置、并行完成集合及已保存的展开子流程，继续未完成实例。**不再从头执行 JavaScript 脚本来猜测恢复位置。**

恢复默认保留当前项目代码。项目或产物变化使原结果不再可信时暂停核对，不能自动回滚或盲目复用。结果不确定的写活动进入 unknown，先确认部分效果。

“从此节点重新执行”创建新尝试和执行代次，使其实际依赖后继失效并重新求值；不能靠全局任务序号切掉后半段。既有下游副作用不能因重试被自动撤销或重复。

## 6. 明确默认语义

| 项目 | 默认值 |
| --- | --- |
| 并行失败 | fail-fast：停止新派发，请求取消其余分支；等待实际退出后汇合 |
| 整个活动自动重试 | maxAttempts = 1；只读或有可验证幂等机制的活动才显式开启重试 |
| 节点内工具纠错 | 普通工具错误返回同一 agent 上下文，模型在节点预算内处理；不通过重启整个活动纠错 |
| 暂停 | 停止新派发，让当前活动完成，进入稳定暂停点 |
| 停止 | 请求取消、等待真实退出，执行已声明且获授权的有限收尾 |
| 强制终止 | 不保证业务清理完成；无法确认的活动进入 unknown |
| 恢复 | 保留当前文件，复用核验通过的已提交输出，继续未完成实例 |
| 定义更新 | 生成新 revision，只影响新运行；运行中实例冻结原快照 |

并行也可以明确选择 allSettled 或其他受支持策略，不能由前端聚合颜色来决定其含义。取消请求发出不等于任务已停止；unknown 活动未核实前不能释放其可能仍占用的写资源并启动另一个写任务。

引擎自有进程/临时资源回收与业务 finally 分开。业务清理有原授权范围和时间上限；审批拒绝不能经清理节点重发原动作。清理成功不能覆盖主错误。

## 7. 动态能力只有一个入口

expand 的输出必须是同版本 Schema 的结构化子流程。先校验、确定摘要并持久化，然后再激活子实例。

校验包括节点数、深度、循环上限、并发、输入输出、目录、工具、网络、预算和命令引用。动态子流程只能缩小原授权，不能增加权限或引入未经批准的命令。

恢复使用已保存的展开结果，不重新询问模型生成另一份计划。不能返回 JavaScript 作为表达不出来时的逃生口。

这样既能在运行时按结果生成更多任务，也能保证任务一旦开始执行，就具有确定的结构、身份和归属。

## 8. 面板只投影，不判断流程

后端返回同一份定义和实例状态的投影，带状态版本与事件游标。面板只负责布局、交互和显示。

- 运行前显示确定的控制结构及尚待生成的 expand 容器。
- 运行中用真实实例事件高亮路径，未选中的分支只针对这次 choice 实例。
- repeat 展示一个循环容器、已执行轮次及实例选择器。
- map 展示集合数量、完成数量和各项实例，不把每轮永久铺满画布。
- 并行展示真实分支、等待汇合与取消状态。
- 节点侧栏绑定明确 instanceId 和 attemptId，显示简要过程、根因及开发日志。
- 实时刷新与编辑草稿分离；刷新不重建弹窗和参数输入。
- 事件断档时重新获取权威快照，不能补猜路径。

默认业务视图展示任务和业务决策；诊断视图展开错误传播、清理、各实例与尝试。它们是同一模型的不同展开程度，不是两份流程。

运行失败、活动失败、业务结果为否、已处理错误、等待宿主与副作用未知各自明确。面板不得将活跃实例标成“未进入”。

## 9. 原生工具、权限与复用

复用已经验证的 Codex 原生 worker 接口、MCP 授权核验、目录身份检查、工作区与进程退出机制；不复用旧脚本调度与旧数据协议。

Run 的授权明确项目、工作区、读写目录、保护目录、网络、MCP 和维护范围。活动只能使用该授权的子集。节点的 read/write 标签不能替代底层原生沙箱或 MCP 每工具授权；未声明副作用的命令按可能有副作用处理。

本地、快照、Git 隔离是文件执行位置与交付策略，和工作流结构分开。更新项目将触及保护目录时，要在工作树写入之前发现能力不足，而不是等 Git 部分更新后才报错。

工作流库保存与项目无关的定义；项目路径和本次授权只属于 Run。在其他项目使用同一定义时创建新 Run，面板固定当前聊天项目。

定义内容、参数、模型配置和工具要求只记录一次。发布插件不包含开发者本机路径、私有文件引用或工程设计文件依赖。

## 10. 删除的旧架构与切换边界

移除任意 JavaScript 编排入口、QuickJS 调度脚本回放、AST 提取流程、源码偏移 nodeId、注释标签、opaque 自由代码回退，以及面板从任务数组反推依赖和状态的逻辑。

新引擎使用独立存储版本，不加载、不执行、不迁移旧定义、运行或检查点。切换前确认旧运行与 worker 已实际退出。旧目录的数据保留或彻底清理属于独立、明确的数据操作；不兼容本身不授权自动删除用户文件。

新版 Skill 和 MCP Schema 只教授新定义协议。需要的任务由 AI 按用户目标重新创建，不通过保留旧引擎实现“临时兼容”。

## 11. 实现顺序与验收要求

| 阶段 | 交付和完成条件 |
| --- | --- |
| 1：定义与编译 | 固定 Schema、表达式与作用域；由同一可执行流程树产生调度和计划图 |
| 2：持久执行核心 | 实例、事务提交、派发意图、结果核验、资源锁、暂停停止和崩溃恢复 |
| 3：工具与动态展开 | agent、command、原生工具及 MCP 范围；expand 与 subflow 在执行前验证 |
| 4：面板与操作接口 | 共用后端投影；循环/分支实例选择、节点过程、参数和更新冲突保护 |
| 5：真实验收与发布切换 | 用真实项目任务核对端到端行为，更新技能、构建自包含包并停用旧引擎 |

不再为旧图补规则，也不设置旧脚本迁移阶段。先完成小而完整的执行语义，再扩展新的节点类型。

验收必须覆盖：多路条件、两层循环、零轮与提前退出、并行乱序和单支失败、动态集合、错误处理与清理、暂停停止、写操作结果未知、进程崩溃、定义更新、节点重试、跨项目复用及彻底删除运行自有数据。

准入标准：实时运行、界面刷新、进程重启和事件重放得到同一份实例状态；每次派发、每条实际路径、每份日志和每个可恢复结果都有可核验的归属。

## 13. 0.10.0 实现与本次验证边界

实现入口为 definition.ts、structured-store.ts、structured-executor.ts、structured-driver.ts、structured-projection.ts 和新版 MCP/面板。旧 JavaScript/QuickJS 执行器、AST 推图、脚本恢复、旧模板与运行协议已移除；旧用户数据未自动删除。运行使用独立 structured-v1/workflows.sqlite，不读取旧 JSON。

实际工具使用 nested grants：workflow_preview 接收 {projectPath,definition,args?,grants?,limits?,sourceDefinition?}；workflow_save_template 更新需要 id 和 revision；workflow_get_run 返回 {run,projection}，scopeInstanceId 选真实轮次/集合项。重试使用 instanceId，不使用旧 taskId。恢复与删除分别核对最新 revision 和确认指纹。

定义、单份参数和节点输出的总序列化 UTF-8 上限是 512 KiB，计入字段名、转义和标点；定义最多 500 节点、24 层结构，repeat 最大 1000 轮，并发最大 32。内部表达式环境允许多份已提交输出，另有 32 MiB 字节边界与复杂度限制。Run 总实例、调用、时间与 Token 预算独立生效。达到循环上限表示编排正常退出，不自动证明业务成功。

循环/map 每轮、每项创建独立 scope 实例，动态子流程以 owner frame 隔离局部节点 ID。已走连线读取实例 cursor 中持久 transition 证据，进度事件窗口滚动不会丢失早期路径；run.events 仅提供有界诊断窗口。未走的计划路径不伪装为实际执行。
