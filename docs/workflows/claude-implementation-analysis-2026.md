## 已确认的设计原则

1. **Agent 生成编排，用户描述任务。** Workflow 是工具入口，支持 inline script、脚本路径、输入和恢复标识。首次任务不要求用户先去 UI 编写脚本。保存脚本让下一次编辑和复用成为可能；保存运行记录与保存定义是两种用途。
2. **脚本是编排层。** 分支、循环、并行、按条目流水线和结构化输出由脚本表达。实际文件读取、命令、修改与 MCP 操作由代理的工具执行层完成，不能只返回模拟报告。
3. **通用性来自工具与权限传递。** 内部 workflow-subagent 的工具声明为 `tools: ["*"]`，并排除会递归创建代理或工作流的入口。派发中存在父工具集合、根工具表、权限上下文、取消信号与调用者身份的传递。具体每次调用的允许范围仍由执行层检查，不能把这条声明解释为无条件全权限。
4. **停止必须等实际任务退出。** 任务注册表与代理控制器关联，停止作用于派发与运行中的代理；退出未完成时重新启动会造成重复执行，必须有互斥与实际退出验证。
5. **恢复依赖 journal 与输入身份。** 不能只按任务序号复用旧结果。脚本、参数、代理选项和工作上下文发生变化后，应重新检查缓存身份与恢复边界。
6. **已有代码与启用功能分别记录。** 普通 Workflow 工具中的 v2 扩展获取函数 `we()` 在这份样本里返回空。world 数据结构、v2 run-op 扩展与兼容代理执行路径需要分别检查；不能因发现 v2 字符串就声称 v2 全部启用，也不能因一个扩展未启用就声称全部 world 路径不存在。

## 对 Codex 插件的实现约束

Codex 原生执行能力通过官方 `app-server` 的 thread/turn 与 command/exec 协议接入。原生文件读取、命令执行和代码修改是 worker 的基础工具；MCP 只增加外部能力。原生工具是否实际使用，应以真实命令、修改事件及独立测试结果为证据。

插件进程没有已经验证的接口，能自动取得当前桌面聊天全部专属工具和授权上下文。独立 app-server 的原生工具、用户配置的 MCP、父桌面聊天专属 apps/图像生成/界面控制必须分别说明。`dynamicTools` 允许受控宿主注入工具，但它本身不会自动连接到父聊天的工具表；不能用未验证的内部接口伪造这种继承。

工作流每个业务需求不应改变插件代码。插件提供通用的代理、并行与流水线、可选确定命令操作、执行范围、持久化、取消、审查和应用能力。Git 与 MCP 配置维护是这些能力上的操作，不是写死 REA 名称、仓库目录或构建命令的专用更新器。具体命令、目标服务器及输入由本次工作流计划表达。

MCP 服务名白名单不能替代每工具权限，文件 sandbox 也不能限制 MCP 服务在其进程中产生的外部写入。需要保留用户已有的工具过滤与审批策略，并核对有效工具列表；尚未支持的父宿主工具必须明确报告。原生联网仅在已经授权的范围内启用。

持久化不能承诺任意外部副作用 exactly-once。失败或中断后的命令、远端修改可能已经部分发生，恢复必须校验状态；外部非幂等操作需使用服务端幂等键或人工核验机制。不能把重放缓存当作事务回滚。

## 验收要求

- Agent 通过实际 MCP 工具创建、启动、读取与恢复工作流；不以直接调用内部 engine 代替产品入口验收。
- 真实 Codex worker 调用原生命令和修改工具，独立测试验证最终结果；代理说“通过”不足以验收。
- 已授权 MCP 在 worker 中真正初始化并被调用；未授权或被用户禁用的工具不得暗中开放。
- 停止后实际子进程退出；另一面板/服务器实例能读取并控制同一运行；重启不自动产生新的副作用。
- 网络、Git 元数据、构建产物、配置写入与恢复状态分别验证。不能把文件快照冒充完整 Git 工作区。
- 安装的新包与当前 App 已加载的包分开验证；配置修改和活动 MCP 连接刷新也分开验证。只有当前连接身份确实更新才能报告已生效，否则记录 `pending_restart`。
- 在脱离开发仓库的发布包中验证，所有引用只能依赖包内文件。开发研究文档不得成为发布 Skill 的运行前置条件。
