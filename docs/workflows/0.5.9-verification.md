# Workflows 0.5.9 验证记录

## 原因与修复

用户从 REA 项目下的“查找项目工作流”聊天打开面板，项目却为空。实际宿主查询返回该聊天为 local Codex，执行目录为 REA，但 projectId 为 null。旧逻辑只认可显式 projectId，因此把侧栏中已经按目录归类的聊天误判成无项目。当前服务确认为 0.5.8，不能用版本未加载解释这次问题。

显式本地项目 ID 仍然优先；仅在本次真实 caller 聊天没有显式项目时，使用宿主返回的该本地 Codex 聊天执行目录，与宿主本地项目库存进行 realpath 后的唯一、精确匹配。显式未知 ID、远端／非 Codex caller、缺失或相对目录、无匹配、同目录多项目和 caller 冲突均不扩大归属。插件进程 cwd、环境变量、工具参数、其他聊天及父目录不参与推断。

项目绑定后仍不可切换目录；跨项目复用仍在目标项目创建独立运行。无法确认时展示具体原因，避免一概提示用户没有从项目打开。同步面板 App 握手版本。

## 验证

私有协议夹具重放本次真实宿主项目与聊天快照，安装包 0.5.8 确认返回无项目；该夹具只替代项目管道，不向真实桌面伪造另一聊天身份。同一宿主快照重放到 0.5.9 运行包后，`workflow_get_projects` 返回绑定 REA、`contextSource: thread`、`bindingSource: thread-cwd`。继续通过正式 MCP SDK 读取 REA 的 4 条已有运行及完成记录详情，状态为 completed/review ready；原 run.json 逐字节不变，未新增 worker。这里验证的是实际宿主数据的私有协议回归，不是替另一真实聊天发起宿主请求。

`npm run check` 通过：424 项运行时检查，423 通过、1 项默认跳过；18 项可移植性、类型、构建和隔离包检查通过。包含共享 provider 并发响应逆序不串项目、显式项目优先、同目录歧义、路径别名、远端与缺失 caller 负例。面板回归覆盖固定项目、历史摘要与详情加载，未调用执行工具。

GitHub 安装包验收在发布后补充；真实 App 面板需加载新版服务，不能将协议回归当作当前旧面板已经刷新。

本轮未迁移聊天归属、修改 REA 项目或启动／恢复／应用任何工作流。
