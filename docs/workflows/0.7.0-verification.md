# Workflows 0.7.0 设计与验证

## 根因与方案

最新 REA 运行 `wf_7a3b7b44c7f24f82f59d63a4` 在 2026-10-15 14:37:06—14:41:21（Asia/Shanghai）执行。预检通过，源码从 `788964d…` 快进至 `ab45bf641e95a56a9d6cb8d246818a3d6925eb41`；安装命令返回 exit 1，后续元数据、构建、检查、doctor 和连接验证未执行。模型生成的 Node 包装捕获了 npm 输出，却只输出退出码，finally 又删除了 npm 临时日志。没有现存证据证明底层是网络、权限或 lockfile 故障。

旧脚本同时要求任何失败立即停止、不重试。用户本次明确要求普通工具错误允许模型纠正和重试，因此需要调整这一任务约束，不能仅升级运行器并声称旧约束已经改变。

[Claude Code 对照研究](claude-reliability-2026-10-15.md) 结合 REA 静态语义与只读源码核对，确认普通错误作为带调用 ID 的工具结果回到同一 Agent 循环；结构化输出、无进展恢复、拒绝和取消另有边界。这是静态机制参考，未运行 Claude，也不宣称完整重建所有动态关系。

本版采用三层方案：

1. 原生工具的普通错误保留在同一 worker 上下文，由模型按真实原因纠正。插件不因一项工具失败自动中止原生回合；任务也不默认写成失败即停。
2. `schema` 检查返回格式，独立的 `accept` 检查明确的成功条件；`maxRecoveryAttempts: 0..2` 允许同一个临时线程增加有限的结果恢复回合，默认 0。保留上下文、原 Task 和权限，不从头重启工作流。格式纠正只要求修正返回值，业务验收不通过才按原授权核对剩余工作。
3. 固定命令可使用预声明的 `operation(id)`，由执行器直接保存 exit/stdout/stderr；通用编程和判断仍由 `agent()` 完成。两类执行可以在同一流程组合，不增加 REA、npm 等业务专用分支。

成功条件校验验证的是返回数据；重要外部事实仍须有真实工具结果或独立验收，不能以一个模型自报的布尔值代替执行证据。

## 实现边界

- 新恢复回合保持模型、深度、沙箱、网络、MCP 过滤与原生审批设置。首个模型回合开始的总执行超时覆盖全部恢复回合，启动阶段沿用独立启动超时。已观测 Token 门槛通过并行 worker 共享的实时余额控制新的恢复回合，在异步范围校验前后和发送前再检查；不宣称精确账单上限。
- 只恢复已完成回合后的 JSON 解析、形状或明确验收失败。原生回合失败、协议错误、用户取消、审核拒绝/超时/中止、原生明确的 approval-never 阻止不恢复。精确原生审批阻止会立即中断；任意 MCP 结果中出现相同字符串不会被当成原生审批决定。
- 校验器使用现有 MCP SDK 的公开 AJV 接口，预先检查有界本地安全子集，不解析引用、正则或 format；不转换类型、补默认、删字段或输出原值。未声明 accept 时，任意 `status: failed` 仍可作为正常分支数据。
- 失败输出、工具、线程/回合、用量及实际恢复次数保留。旧完成缓存重新核对当前契约；不合格时要求明确重试，不悄悄重复已经发生的操作。
- 宿主 Error 通过不透明身份跨 QuickJS 保留。脚本保存原 Error、完成 finally 后重新抛出，可准确记录 task/attempt/phase；新的独立脚本错误不会被旧错误覆盖。脚本自行字符串化后丢失的因果关系不靠猜测补齐。
- 识别明确失败的 dynamicToolCall 和带显式错误 envelope 的 functionCallOutput，记录有界脱敏诊断。普通输出含 error 字样不作失败推断；参数、成功载荷、reasoning 不进入这类诊断。未从子程序输出的数据无法还原，不能以日志扩展宣称已经修复所有吞输出路径。
- `maintenance.steps` 与 `operation(id)` 支持三个显式可写工作区模式，仍只执行预声明 argv。activation 和 protectedPaths 仅 Git 隔离；本地旧记录不能借新增命令扩大 Git 写权限。派发时重新验证工作区身份和归属，保留幂等声明、结果未知保护及原有精确网络重试。

Codex 原生接口依据：[App Server 的回合、工具结果与事件](https://learn.chatgpt.com/docs/app-server)。没有接管或绕过原生审批，也没有新增可由模型任意传 argv 的宿主动态工具。
