# Workflows 0.9.0 控制流与进程生命周期

日期：2026-10-15。此文为工程验证记录，不随插件发布，不作为 Skill 执行前置资料。

## 问题与行为

旧面板将阶段排成横列，不能清楚表达条件分叉、汇合和循环回路。打开面板还会在聊天中显示完整内嵌界面；并行读取设置会启动多份临时模型目录查询。版本更新后，旧聊天连接仍可保留旧服务，因此仅看到多个 Node 进程不能确定是哪一层造成。

本版提供可解析源码结构和本轮执行观测：条件使用菱形、两路与汇合，循环使用分组、轮次和回边，并行区域保留独立分支。节点打开右侧过程栏，继续支持简要过程、开发日志、历史尝试、停止与检查点恢复。视觉依据见[选定方案](visuals/0.9-selected.png)，实际交互范围见[浏览器验收](0.9.0-design-qa.md)。

结构是展示元数据，不替代原工作流。`flowNodeId` 绑定调用位置，同一位置重复执行仍产生各自 task/attempt；每次开始或恢复产生新的 `flowExecutionId`，避免旧任务伪装为本轮执行。条件、循环在脚本实际执行时产生 `flowEvents`；缓存结果在恢复时明确标识。

## 结构与执行边界

- 计划最多 200 个块，深度 12，安全名称最多 80 字；路径记录最多 2000 条。截断后，旧判断不继续排除其他分支，旧轮次只称已记录范围。
- 可选的紧邻注释 `// @flow-label: 验证与修复` 用于显示名称。不会从条件表达式、普通字符串或执行结果猜测业务名称。
- 只有静态可核验的字面计数循环才展示最大次数；`return`、`throw`、`break`、`continue` 保留终止语义。显式标签跳转不猜测最近循环。
- 参数求值顺序、短路、循环控制和原异常传播保持原行为。别名、复杂函数、动态区域保留实际任务回退；动态执行及可识别源码反射不插入观测。不声称任意 JavaScript 的完整依赖图均已恢复。
- 辅助变量名只按真实 AST 标识符选择有界数字候选，避免长下划线字符串导致反复扫描源码或生成超长名称。
- 新图不修改原脚本、文件权限、网络、MCP 授权或审批。检查点仍保留当前代码，不隐含文件回退。

## 进程实测与修复范围

修改前的本机快照发现三份 Workflows：一份 0.8.0、两份 0.7.0，均为同一 Codex app-server 的直接子进程。其他 Node 还包含其他 MCP，不作为 Workflows 泄漏计数。本次没有终止这些真实聊天服务或改写用户全局配置。

源码核对表明：面板仅通过 MCP 调用工具，不派生系统进程；launcher 的 `execve` 原地替换进程；QuickJS 使用 worker thread，不产生独立 Node PID。stdio 每次宿主连接创建自己的服务；插件没有可使整个 App 全局共享一个 stdio PID 的公开开关。本版不以增加代理或改变进程名称冒充全局单例。

实际优化：

1. 同一真实目录的并发模型目录发现共享在途会话。订阅者独立取消，最后取消等待真实进程清理；新的查询不会与正在取消的旧进程重叠。完成后仍读取新配置，不复用 worker 或扩大授权，返回数据各自复制。
2. 配置激活辅助 app-server 与其他配置会话一样禁用 plugins/apps/remote_plugin，保持配置读写用途。本次没有证明旧配置读取必定递归启动插件，因此不将此项称为已复现的递归泄漏。
3. stdio 服务监测启动它的父进程。父进程消失时走真实关闭流程；即使执行器或存储清理报错，也在 finally 关闭 MCP 传输，避免遗留读管道让进程继续常驻。
4. `workflow_get_capabilities.runtimeLifecycle` 明确提供 PID、父 PID、按宿主连接的作用域及 `globalSingleton: false`，便于核对，不承诺运行任意外部工具时整个进程树只有一个 Node。

两场真实 Node 进程测试用独立父进程启动生产 stdio 入口，再杀掉自己创建的父进程；测试方仍保留 stdin 连接，所以没有 stdin EOF。正常关闭与注入后端清理异常两场均验证服务退出。Windows 仍有父 PID 存活检查，但本次真实父进程强杀验证在 macOS 上执行。

## 全屏显示

资源和 App 初始化均只声明 `fullscreen`，避免聊天内重复完整面板。当前宿主仍控制简短的打开记录和重开入口，插件不请求隐藏工具记录、不改工具可见权限、不使用 first-party 私有字段。

依据：[OpenAI 显示模式声明](https://developers.openai.com/plugins/reference#declare-display-modes-before-the-ui-loads)、[工具 meta 字段](https://developers.openai.com/plugins/reference#_meta-fields-on-tool-descriptor)、[Codex MCP 接入方式](https://learn.chatgpt.com/docs/extend/mcp#configure-with-configtoml)。本机宿主渲染源码也将非 inline 视图映射为 launcher，不等同于删除聊天项。

## 真实模型与持久化恢复

`checkpoint-real-smoke.ts --real-workers --control-flow` 在一次性非 Git local 项目中完成真实原生命令，实际配置为 `gpt-6-luna/max`：

1. 首节点独占创建随机标记并读取核对。
2. 真正进入“写入已通过”条件，开始两轮独立读取循环。第二个任务首次在 native 调用前受控挂起，随后停止并关闭 Engine。
3. 重开只读预览不调用模型；确认恢复后复用首节点，两个循环读取分别由真实 native worker 完成。
4. 三次真实 native 调用，attempt 数由 `[1,1]` 变为 `[1,2,1]`；首节点 attempt 完全不变。两个读取共享同一静态 callsite，但 task ID 不同，均属于新的执行 ID。
5. 条件观测为 true，循环观测 `[1,2]`，最终八个已提交 checkpoint，完成任务数 3；文件保留，用户配置字节摘要不变，全部临时数据与凭据已清理。

本轮约 42.7 秒，脚本 SHA-256 为 `37a80fefc9af66aeca3d58d4a09031f6cb7d2e4f5c37fa36427b142c5827f489`。原生工具证据均包含 `native:commandExecution`。受控挂起位于 native 派发前，不宣称真实模型进程崩溃恢复；真实 owner SIGKILL 由独立检查点测试覆盖。

## 验证状态

最终冻结源码的 `npm run check` 退出 0：825 项运行检查，823 通过、0 失败、2 项按平台或显式开关跳过，耗时约 255 秒；另有 18 项移植性测试通过。跳过项为可选真实命令沙箱测试及 Windows 专属命名管道测试，本次未冒充为已执行。

清单与技能引用链验证覆盖 180 个插件文件；所有运行包重新生成。独立 MCP 客户端从非工程目录启动运行包，在私有临时数据中执行无模型的条件与两轮纯控制循环，返回 2，实际记录 true 和 `[1,2]`，原文件保留；相应 UI 回归确认这种无 worker 但有可信观测的完成循环显示完成，截断或未观测场景仍不猜测。

真实原生加载器已核对 24 个工具、全屏资源与仅项目聊天入口；两种有效配置均验证 Workflows 是该 Codex host 的直接子进程，重复打开两次面板的 PID 保持不变。该验证使用临时 home 和市场，0 次模型推理，用户配置不变；它不证明整个 App 的所有聊天共用一个实例。

GitHub 安装包一致性、已安装版本及当前聊天实际加载版本分别报告，不能把 CLI 安装成功等同于当前桌面连接已重载。
