# Claude Code 动态工作流脚本契约研究

研究日期：2026-10-14。对象为 Claude Code `2.1.296` 的当前取样构建。结论来自 REA MCP 静态分析和按原模块名进行的 AST/字节范围核对；没有执行原产品或复制其源码。本文是开发研究，不属于发布 Skill 的前置资料。

## 结论

Claude 的动态工作流以 JavaScript 脚本表达本次编排，由调用代理生成或复用。引擎固化的是解释执行、并发、权限、日志、恢复和生命周期；任务分解、条件分支、循环、验证与汇总由脚本表达。源码没有要求终端用户手写脚本，也没有为每种需求新增引擎实现。

首次调用可直接传入 `script`，按名字复用已保存定义，或读取 `scriptPath`。每次执行都有运行标识、脚本文件和 agent journal。脚本变更后可基于原运行恢复，重新执行变化位置及受影响的后续调用。

本构建中普通 Workflow 工具的 `runId`/world 扩展提供函数为空，但普通脚本执行仍通过注入的 `call.runEngine` 启动。不能将“该扩展未启用”扩大为所有 v2 引擎不存在或不能运行。

## 已确认：脚本表达力与引擎边界

`YS` 解析普通 JavaScript，允许顶层 `await` 与 `return`。第一条语句须导出纯字面量 metadata；计算属性、变量、函数调用、展开或插值不能作为该纯字面量的任意替代。解析器确认 `name` 与 `description` 为非空字符串，允许可选标题、使用说明及阶段。当前证据不支持把本插件的小写短横线命名规则说成 Claude metadata 解析器的要求。

编译函数 `qie` 将主体编译成异步脚本；`lXn` 构造受限 VM，绑定 `agent`、`parallel`、`pipeline`、子 `workflow`、`args`、日志、阶段及预算相关能力。任务自身的文件、命令和修改在 worker 中处理，编排脚本不直接访问 Node/文件系统。控制流可按实际返回值产生新任务和停止条件。

| 由脚本决定 | 由引擎固化 |
| --- | --- |
| 任务目标、输入集合、worker 提示和结果 schema | VM、值传递、worker 启动与工具权限上下文 |
| 条件分支、有限循环、下一批任务和合并方式 | 并发上限、队列、预算检查及取消信号 |
| 是否验证、如何对抗复核、是否进入修改阶段 | journal、缓存匹配、重试/停滞处理、真实尝试和用量 |
| `pipeline`、`parallel` 的组合及子工作流调用 | 任务登记、进度、输出与终态清理 |

`parallel` 接受函数数组，等待各项结束并保留输入顺序；失败项记日志并返回 `null`。`pipeline` 让每个输入独立通过阶段，当前输入得到 `null` 时停止其后续阶段，其他输入继续。阶段 metadata 主要服务进度分组，不是预设的“审查→核实→修改→测试”强制图。

已选择的 VM 绑定中没有本插件新增的 `operation` API。它可以作为明确声明 argv 的可选产品能力，不能取代通用 `agent`，也不能被称为已确认的 Claude 同名接口。

## 已确认：返回与恢复

普通工具调用返回后台任务标识、运行标识、摘要、transcript 位置及脚本路径；这与脚本最终 `return` 是两个不同结果。运行结束后登记最终脚本返回值、实际 agent 进度、日志和用量。空结果可能是真实返回值或缓存，不能据此虚构已找出问题或完成修复。

恢复使用先前运行标识及可读取的脚本。`Ir` 检查旧任务是否仍运行，或虽然不显示运行但尚未真正退出；它会拒绝并发重放同一 journal。后台 adopt 还核对脚本内容 SHA，内容变化不能冒充原批准脚本。

agent journal 记录 started/result/failed。缓存键使用 prompt、影响执行的规范化选项及前一调用的 key 连成链；当前规范化字段包括 schema、model、effort、isolation、agentType 和工具限制。变化使后续 key 改变；首个实际失败或不匹配会禁止后续旧结果复用。之前仅启动但没有 failed 的中断调用可以重新启动，同时保留后续独立完成且仍匹配的结果。静态依据为运行时本地 20340–23862、47700–48900。

这是每个运行的 agent journal，不能与 world/founded machinery 的 journal 混为一种缓存。

## v2 条件门控：已确认、推断与未知

已确认：工具模块本地 58155–58176 的扩展提供函数 `we` 为空返回。普通工具的 `runId` 校验与调用分支先检查该提供函数，未取得扩展时分别拒绝或抛错；因此不能把 runOp 字段、world script 更新及相应扩展提示称为这条普通工具路径的已启用能力。`st`/world 恢复在该模块的两个调用点也受这个分支限制，不是普通 script/name/path 调用的必经步骤。

已确认：普通 local-launch payload 本地约 70831–71221 未提供 `v2Run`，但会把执行函数与 payload 交给外部 `call.runEngine`。执行函数 `ejt` 接收可选的 `e.v2Run`；存在时会登记到任务。registry 的 pause/kill 会调用它，旧 checkpoint 路径会排除带该字段的任务。源码保留这些挂钩不证明普通 payload 已触发它们。

推断：所选普通 Workflow 工具静态主路径使用已确认的脚本解析、VM 与 agent journal 契约。不能仅靠 world 类型名或 `v2Run` 字符串扩大可用 API。

未知：外部 `runEngine` 是否会在其他场景动态注入 v2 payload，以及其他产品构建、策略或宿主是否启用这些扩展。未进行原产品运行观测，本文不宣称所有 world/v2 引擎均不可用。

## 对本插件的建议

1. 主流程由代理将自然语言任务转换为本次脚本与明确执行范围，保存预览并在已有授权下直接使用工具执行；编辑器保留为高级入口。
2. 引擎提供稳定的通用编排、worker、权限与恢复能力。任务变化主要产生新脚本和输入，不应频繁增加特殊业务工具或固定流程。
3. 让 worker 使用真实的原生读取、命令、补丁和明确授权的现有 MCP；不要把父聊天的桌面工具或私有连接器说成全部继承。
4. 把通用 agent 任务与可选的预声明维护 argv 分开。网络、写入、工具白名单、workspace 和激活范围须进入预览和版本核对。
5. 区分脚本完成、实际改动应用、激活配置写入、宿主重载与最终版本验证；部分失败需要可重试的真实阶段状态。
6. 新能力、缓存键变化和新增授权范围都要做针对性测试；不把静态参考、测试替身或 tool-list 可见性当作真实执行验收。
