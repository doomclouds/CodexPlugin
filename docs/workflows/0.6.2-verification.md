# Workflows 0.6.2 验证记录

## REA 三次运行的原因

第一次运行的只读预检继承了全流程的 `rea.binary_session` 授权。该工具的 REA 合同明确包含 `launchesProcess`，推导 `readOnlyHint: false`；旧适配器因此在模型执行预检前拒绝整份授权。修复只读节点的工具投影，不修改 REA 业务源码或它的正确合同。

第二次 worker 自行生成的 zsh 代码给 `status` 赋值，真实日志为 `read-only variable: status`。这是命令编写错误；预检按流程要求返回 blocked，没有开始拉取或构建。第三次预检使用 here-document，zsh 要创建系统临时文件，真实日志为 `can't create temp file for here document: operation not permitted`；可写项目沙箱也不开放系统临时目录。

REA 对话随后已把预检改为固定的 `node -e` 命令。本轮在该最新定义的版本保护下，只将预检恢复为只读，保留实际 MCP 验证节点的写入模式、既有白名单及执行范围，没有重放三个失败记录。worker 通用执行说明补充任务专用变量名、直接 argv 和不落盘的检查方式，避免每个业务流程反复生成相同的易错 Shell。

## 插件修复

适配器先完整验证显式工具集合确实存在、未被用户过滤禁用，再给只读节点投影明确的只读交集；空交集禁用对应服务，原生只读工具保持可用。写节点保持原显式集合，输入授权对象不修改。启动后的实际工具集合和实时注解再次核对，注解丢失或从只读变成非只读会在派发模型任务之前拒绝；审批、用户过滤及递归防护保留。

面板的租约请求与项目、运行、模型、工作流库同步拆开。慢读取期间仍正常续租，必要项目与运行信息确认后结束主同步；模型与库后台加载，不放宽未确认详情的操作权限。

日志包含两个独立阻塞原因：旧后端等待终态检查点与锁清理后才读取节点诊断；旧前端开发日志请求可能在连续进度刷新中不断被废弃。新增 `getNodeProcess` 只投影有界诊断，不等待终态收尾，也不返回脚本、revision 或工作区权限。完整详情、停止和执行操作仍保留原有等待与锁语义。

弹窗读请求保持单飞，连续进度合并为下一次刷新，当前响应先展示再读取新值。简要与开发日志分别排队，切节点或关闭使旧响应失效；失败明确显示可重试入口，不自动无限重发。由于宿主调用不提供安全取消，旧请求实际结束前不会堆叠新的并发请求。

## 验证

新增回归覆盖只读／写入混合授权、没有安全工具的节点、未知与禁用工具、缺少或变更只读注解、超过租约时长的慢同步、简要与开发日志公平读取、关闭和错误重试，以及终态收尾被门闩阻塞时的诊断与操作边界。

`mcp-scope-real-smoke.ts --real-workers` 使用隔离配置和临时 MCP 服务，运行三个实际 gpt-6-luna / max worker：只有非只读 MCP 授权的预检仍可运行准确的原生 `node -e` 检查；写节点实际调用唯一授权的非只读探测工具；混合授权的只读节点只实际调用只读工具。三者的原生／MCP 调用证据、服务端调用记录和原项目文件均核对通过。MCP 服务是标注真实合同的测试夹具，模型、CLI 和工具协议是真实执行；这不是 REA 拉取构建或父聊天重载验收。

REA 最新固定预检命令另通过真实 gpt-6-luna / max 只读 worker 验证，返回 `ready`，没有调用不符合只读合同的 MCP。执行前后源码与 Git 语义摘要一致，未执行更新或构建；这次是单节点验证，没有恢复原维护运行。
