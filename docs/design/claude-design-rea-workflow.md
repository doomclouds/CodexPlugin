# Claude Design 与 DesignSync：REA 工作流和架构研究

研究日期：2026-10-16。样本：本机公开发布的 Claude Code 2.1.296 二进制及其中内嵌的 JavaScript、DesignSync 资源。本文是工程研究，不是发布插件的运行依赖。

## 结论

1. **[源码观察] Claude Code 的 Design 接入以项目文件和真实组件代码为中心。** `ClaudeDesign` 操作远端项目、文件、会话和渲染；`DesignSync` 将既有 React 组件库及其样式、类型、使用说明和预览转换为 Design 使用的资源。不能将它概括为“生成一个场景 JSON，再画成 HTML”。证据：S1、S2、S3、S4、S5。
2. **[源码观察] 设计系统导入是一条带视觉验证和增量依据的构建流水线。** 编译产物、组件 API、CSS 引用闭包、浏览器渲染、故事参考、模型审阅和同步锚分别承担不同职责。文件写入成功不等于组件可用，也不等于视觉验收通过。证据：S4—S8。
3. **[官方公开] 2026-10-16 的产品基准已包含聊天中的 Design Artifact。** 官方已公布独立站点于 2026-12-14 关闭；新设计、设计系统和幻灯片进入 Artifact 体系。不能只复制旧独立站的项目列表。来源：[迁移说明](https://support.claude.com/en/articles/17440474-migrate-from-standalone-claude-design-to-claude)。
4. **[本仓库观察＋推断] 当前 `plugins/design` 建立了本地文档、编辑、并发保存和受限源码往返，但还不是这个级别的产品。** 它的组件是 `DesignNode` 子树，独立模型提交 JSON Patch，预览是受限静态投影；真实组件运行时和代码工作台尚未建立。要对标并超越，应调整设计源、预览和验证架构，而不只是给现有属性面板增加按钮。依据见第六节。

## 一、ClaudeDesign 的实际工具面

### 项目、文件与渲染

**[源码观察，S1]** 顶层工具名称为 `ClaudeDesign`，输入为 `{ operation, arguments }`。`operation` 选择动作；并不是每次注册一个固定设计节点工具。`list` 通过 MCP `tools/list` 发现服务端目录，可要求 `full`；目录摘要可按会话哈希缓存。

| 类别 | 确认的操作 | 客户端确认的关键输入 |
| --- | --- | --- |
| 设计上下文 | `list_design_systems`、`get_claude_design_prompt` | 后者接受 `design_system_id`、`project_id` |
| 项目 | `list_projects`、`get_project`、`create_project` | `project_id`；创建接受 `name`、`design_system_id` |
| 文件读取 | `list_files`、`read_file` | `project_id`、`path` |
| 文件写入 | `write_files` | `project_id`、`plan_token`；每项可带 `path/data/local_path/encoding/if_match` |
| 文件复制与删除 | `copy_files`、`delete_files` | 项目、授权计划；复制源/目标与可选源项目，删除路径与可选 `if_match` |
| 运行支持与预览 | `create_support_js`、`render_preview` | 支持脚本路径；预览接受 `project_id/path/render/validators` |
| 设计会话 | `get_conversation`、`put_conversation` | 读取 `chat_id`；写入 `title`、`messages[{role,content}]` |
| 协作与分享 | `list_members`、`add_member`、`remove_member`、`update_member_role`、`update_sharing` | viewer/commenter/editor；邀请或组织可见；view/comment/edit 链接权限 |
| 授权计划 | `finalize_plan` | 项目及 `writes/deletes` 路径范围 |

**[源码观察，S1]** 客户端先验证已知动作的参数和风险等级。发现的新只读操作可以进入后续调用；新写操作若缺少该客户端的参数验证定义会被拒绝，不能因为服务端宣称可用就绕过本地约束。

**[源码观察，S1]** 写入支持 `if_match` 条件字段，因此协议为调用方保留了防止覆盖旧文件的入口；本轮未观察实际服务器返回的版本标识格式，也未验证冲突的 HTTP 状态及合并策略。

### 用户授权与云端边界

**[源码观察，S1]** 项目首次普通写入可触发一次持久写授权；撤销后需重新获得授权。`copy_files`、`delete_files` 依赖逐批路径计划。客户端已拒绝旧的 `finalize_plan(scope:"project")` 路径，引导使用持久项目授权或具体文件计划。保留路径和不能完整列示的批次另有约束。因此“支持项目级授权”不等于“所有项目文件操作永远不提示”。

**[源码观察，S1]** 实际传输为第一方 `/v1/design/mcp`，包括 `initialize`、`tools/list`、`tools/call`，携带 MCP session ID。客户端限制第一方 API 域名，要求具有相应能力的 claude.ai 认证；它不是本地渲染引擎的另一层名称。

**[源码观察，S1]** 预览返回可包含图片，客户端只转交部分栅格 MIME 类型，并为图片和聚合结果设置约 130,000 字符的保留预算。声明接收 SSE 并不表示实现流式预览：这段客户端在服务器返回 `text/event-stream` 时明确报不支持。

**[未验证]** 没有调用远端目录，无法断言全部当前操作、预览 validator 名称、服务端代码执行沙箱、内部设计文档格式或现有账户权限。工具内的 `get_claude_design_prompt` 从服务端加载实时约定，本轮没有该响应，不能用本地提示文本补造它。

## 二、创建、修改与交付的用户旅程

**[源码观察，S2]** `/design` 是路由入口。无子命令时先获取实时设计约定，再根据用户需求创建或编辑项目。`import` 读取指定项目的元数据、目录和文件到工作目录；`export` 创建项目并上传当前工程；`status` 查询项目和设计系统。`sync/login/consent/revoke` 由专门命令和授权界面处理，不能把这些词误当成设计题目。

```mermaid
flowchart LR
    U[用户需求与既有工程] --> R[命令和项目上下文路由]
    R --> D[发现工具与加载实时设计约定]
    D --> F[读取或创建项目文件]
    F --> W[条件写入与路径授权]
    W --> P[远端渲染与验证]
    P --> V[模型和用户审阅实际结果]
    V --> F
    V --> H[共享或交给代码工程继续实现]
```

图中的步骤来自 S1/S2；**[未验证]** 箭头不代表本轮实际完成了一次远端设计。

**[源码观察，S2]** 工具说明存在两套产品分流。旧路径将 ClaudeDesign 描述为共同编辑的画布；新路径将一般设计交给 Artifact 类型，仅在明确指定独立项目时使用 `ClaudeDesign`。这表明“Claude Code 有 Design”包括宿主 Artifact 与独立项目两条路径，不能仅凭一个工具名推导完整前端实现。

**[官方公开]** 用户端同时提供对话、元素内联反馈和直接画布编辑；画布由画板和可嵌套图层组成。官方还公开了键盘导航和属性编辑行为。[使用说明](https://support.claude.com/en/articles/14604416-get-started-with-claude-design)。

**[未验证]** 本轮 CLI 样本没有恢复浏览器编辑器本体。以下数据合同仍未知：画板序列化、图层与代码位置的绑定方式、实时选中消息、评论锚点格式、协同操作协议、Undo 数据结构。`get_conversation/put_conversation` 只能证明有会话读写，不能证明它们就是评论或选中同步通道。

## 三、DesignSync：导入的是客户真实组件

### 输入和执行位置

**[源码观察，S2/S3/S4]** `/design-sync` 加载随包转换流程。输入分为已存在 Storybook 的组件库与只有编译包/类型声明的组件库。核心是复用客户编译后的实际组件，不要求重新画一份外观相似的假组件。

**[官方公开]** 官方把从代码中的 React 组件同步定位为产品设计系统导入；品牌资产、文档和设计参考是另一类入口。[设计系统说明](https://support.claude.com/en/articles/14604397-set-up-your-design-system-in-claude-design)。

**[源码观察，S3]** `DesignSync` 是另一套工具，输入使用 `method`，并直接调用 `anthropic.omelette.api.v1alpha.OmeletteService` 的项目、文件和素材方法。它专门创建 `PROJECT_TYPE_DESIGN_SYSTEM` 项目；不是 `ClaudeDesign` JSON-RPC 代理的简单别名。

| 位置 | 在发布文件中观察到的职责 | 状态 |
| --- | --- | --- |
| 本地源码库 | 构建组件、读取类型、提取 CSS/字体、生成预览、验证和比对 | 源码观察，S4—S9；本轮未执行 |
| 本地工具边界 | 已批准 `localDir` 下读取真实文件，校验规范路径和 realpath，拒绝越界及非普通文件，限制单文件约 12 MiB | 源码观察，S3 `Se` |
| 远端项目服务 | 列举/创建项目、读写文件、登记/移除组件卡片 | 源码观察，S3；本轮未请求 |
| 远端设计代理 | 消费组件代码、类型、指南和样式创建真实界面 | 随包资源对消费合同的声明，S4；运行未验证 |
| 浏览器编辑器 | 展示组件卡片、实际设计与编辑入口 | 资源声明＋官方公开；内部实现未恢复 |

**[源码观察，S3]** 工具支持 `register_assets/unregister_assets`。卡片元数据包括人类可读名称、预览文件路径、说明、viewport 和 group。这是“组件库可浏览、可判断和可使用”的产品入口，不只是后台组件清单。`localPath` 使已有大文件无需经过模型上下文转抄后再上传。

### 发布资源的数据合同

**[源码观察，S4/S5/S6]** 可确认的设计系统资源布局：

```text
_ds_bundle.js                    实际组件编译包，IIFE / window 命名空间
_ds_bundle.css                  编译组件样式
_vendor/                        运行依赖
styles.css                      设计实际加载的样式入口
tokens/、fonts/、guidelines/      变量、字体及使用约定
components/<group>/<Name>/
  <Name>.html                   人类浏览的真实预览卡片
  <Name>.jsx                    组件相关源码材料
  <Name>.d.ts                   模型使用的 API 类型合同
  <Name>.prompt.md              模型使用的组成方式和范例
_preview/                       可执行预览相关资源
README.md                       设计系统约定与索引
_ds_sync.json                   同步和验证依据
_ds_needs_recompile             发布过程的重编译/刷新标记
```

**[源码观察，S5/S6]** `_ds_bundle.js` 首行有 `@ds-bundle` 头；验证器要求 `namespace/components/sourceHashes/inlinedExternals` 等字段。卡片 HTML 首行有 `@dsCard` 元数据。实际设计只接收 `styles.css` 的传递 `@import` 闭包，不能因为某张预览卡片单独加载了 CSS，就认定设计也会正确显示。

**[源码观察，S5]** `_ds_sync.json` 写出的字段包含 `shape/styleSha/renderHashes/sourceKeys/keyRecipe/scriptsSha/sourceHashes/auxSha/bundleSha12`。局部构建清单 `.stories-map.json` 还包含组件故事对应、exportKey、preview sourceKey 和本机包位置；该清单被明确标为本地材料，不应上传。这与本仓库禁止发布开发者本机路径的要求一致。

**[未验证]** 上述是“设计系统资源格式”，不是“所有设计工程、画板和节点的统一格式”。无法从这套文件布局推出 Claude 画布内核使用何种场景图。

## 四、同步不是文件复制：验证、上传、提交依据分别建模

**[源码观察，S7/S8]** `resync.mjs` 实现构建、远端依据差异、包验证及按范围捕获的驱动；最后输出版本化、机器可读的结论。它同时保留两种变化分区：

| 分区 | 回答的问题 | 核心数据 |
| --- | --- | --- |
| 验证分区 | 哪些组件需要新的截图和判断？ | unchanged/changed/added/removed、pendingGrade、canary |
| 上传分区 | 哪些实际资源需要更新或删除？ | components/deletePaths/bundle/styling/aux |

**[源码观察，S7]** 仅修改 `.d.ts`、使用指南或组件分组，也会影响上传，不能因为截图未变而跳过。相反，构建工具变化导致编译资源变化，不一定清空既有视觉判断；它可以进入抽查集合。`KEY_RECIPE = 7` 显式版本化哈希规则，旧依据与新规则不可比较时有退化路径。

**[源码观察，S7]** 需要注意它的缓存信任边界：这里的 `sourceKey` 重点涵盖故事、手写预览、影响预览语义的配置和覆盖模块，不等于整个实际组件依赖闭包。CSS、共享 bundle 等变化主要进入上传侧；代码中刻意让部分既有评分继续沿用。不能将“源哈希存在”概括为“每次组件实现改动都重新视觉验收”。

**[源码观察，S6/S9]** 验证器检查包头、资源引用、字体、CSS 可达性、类型语法和真实浏览器渲染，能识别空白、占位过薄、变体相同、溢出等错误。Storybook 路线再以客户故事渲染作为参考；无参考路线区分可运行但未精制的基础卡片与已制作的预览。模型评分和结构检查是不同证据，不可互相替代。

**[源码观察，S8/S9]** 驱动 `ok` 为真仅代表相应机械阶段完成，仍可能有 `pendingGrade`。随包验收约定同时要求处理待评分项和未归档问题。缺浏览器而显式接受未视觉验证的产物，与完成视觉验证是两种状态。

### 上传完整性

**[源码观察，S3/S4/S9]** 支持每批最多 256 文件、显式目标计划和本地目录边界。首次空项目可先上传已验证批次，使用户逐步看到内容；既有项目有完整对账路径。发布顺序将重编译标记、内容写入、无用远端资源删除和最终同步依据分开。

**[源码观察，S4/S9]** `_ds_sync.json` 被要求在内容、删除和标记更新之后单独最后写入。原因是不能让一个新依据为半完成项目背书；否则未来增量计算可能永远不补齐遗漏。这是有提交语义的同步协议，而不是“最后记一下文件哈希”。

**[未验证]** 上述顺序来自随包客户端与流程资源，不证明云端整个多文件批次拥有数据库事务，也没有证明任意中断能自动原子回滚。

## 六、与当前插件的架构差距

本节对比的是本轮仓库工作区中的实现，不是已安装版本。`plugins/design/README.md` 已将它标为试用版，并明确真实前端组件和任意工程预览尚未实现。

| 架构层 | Claude 样本中可观察的做法 | 当前插件的实际实现 | 对目标体验的影响 |
| --- | --- | --- | --- |
| 设计的权威来源 | 项目文件、真实组件代码与设计系统资源 | `src/model.ts` 定义有限 `DesignNode` 场景图 | 自定义逻辑和现有组件被压缩成有限节点后，表达上限先于模型能力出现 |
| 模型执行范围 | 通过文件工具读写工程，并调用实际预览；实时设计约定由服务端提供 | `design_apply_changes` 与独立任务主要输出 JSON Patch | 即使用更强 Codex 模型，也仍被限制在同一场景图词表 |
| 组件系统 | 实际编译代码、API 类型、使用指南、真实预览、依赖和样式闭包 | 模型内组件是节点树；`render.ts` 展开为静态 DOM | 看起来像按钮的节点不能替代客户带状态、校验和事件的真实按钮组件 |
| 预览与验证 | 图像回看、浏览器运行、组件参考和机器可读验收依据 | 受限 DOM 投影；PNG/PDF 借 Chromium 输出文件 | 导出截图不等于模型读取了截图，也不等于交互实际运行通过 |
| 源码往返 | 文件级导入/导出；设计系统同步另有构建、差异和提交依据 | `export.ts/sync.ts` 支持自有 JSON 与指定 HTML 内联修改 | 已有安全往返成立，但无法无损承接任意 React/Blazor 工程 |
| 编辑定位 | 公开 UI 有画板、图层、评论与直接编辑；内部代码绑定未恢复 | UI 使用稳定节点 ID、修订号与评论 | 本地定位有基础；还没有真实 DOM、组件符号与源码位置的绑定 |
| 修订与恢复 | 文件条件写入已观察；用户版历史官方尚未提供 | `store.ts` 有本地原子保存、冲突、撤销重做与历史恢复 | 这是当前可以继续发展的优势，不必照搬对方缺少的能力 |
| 分享与协作 | 远端项目、成员角色与分享权限 | 当前本地项目库和 MCP App | 本地单人使用边界清楚，但不是云端多人协作替代物 |

**[推断]** 最关键差距在前四层。扩充节点属性、模板数量或文件导出格式，不能解决“模型无法直接使用真实组件与工程运行时”的问题。当前场景图适合作为快速排版文档或编辑投影，不应被预设为所有设计工作的唯一源。

## 七、面向 Codex 的改进方向

以下均为**推断与建议，尚未实现**。目标是利用本地 Codex 已经拥有的工程能力，形成可编辑、可运行、可验证的工作台。

### 以真实工程为设计源

把项目源文件、依赖、组件 API、设计系统和运行配置作为权威数据；场景树承载可编辑投影和语义定位。模型通过当前 Codex 的正常工程工具修改源码，插件负责工程生命周期、预览、选择定位和验收。既有节点文档可保留为一种轻量文档适配器。

画布改动应产生可审查的源码修改：绑定源文件、组件符号、实例定位和当前工程修订，尽量做窄范围 AST 修改。不能映射的操作明确退回代码修改流程；不得把未知代码重新生成成一份简化 JSON 后宣称无损同步。

### 让模型看到并操作真正运行的结果

预览与导出使用同一份工程及组件依赖。编辑面板向模型提供当前 viewport 的真实图像、选中 DOM 与源码位置、关键计算样式、运行错误和修订依据。模型提出修改后，应经过构建、真实预览和目标交互回读，才能将该迭代标为已验证。

任意代码预览需要独立运行时与受控执行环境，不能直接放进具有 MCP 工具能力的编辑器主页面。MCP App 仍是宿主中的产品入口；受管理的本地服务属于内部实现，不应要求用户自行寻找 localhost 页面。

### 组件导入建立完整合同

从现有工程提取真实组件、属性类型、变体、用法、样式与依赖闭包；提供真实可运行卡片和按 viewport 的质量检查。组件目录应与实际运行包一致，模型使用的组件 API 也应来自同一版本。

需要将“构建通过”“组件运行通过”“视觉对比通过”“用户接受近似”分开。变化检测宜覆盖组件实际实现及依赖闭包，避免仅凭预览包装器未变就沿用对已改变组件的质量结论。可用变化影响分析减少重复验证，但不能把未检查伪装成已检查。

### 用可靠本地状态形成可衡量优势

保留当前原子保存与修订冲突基础，扩展为工程快照、设计方向分支、候选对比和可恢复的运行状态。评论应有“待处理→模型已接收→对应修订已应用→视觉已确认”的证据链；发送聊天消息成功与评论改动完成是不同事件。

对外宣称“超越”之前，应在同一真实组件库和任务集比较：首次生成可用性、目标修改精度、无关源码保留、跨尺寸效果、构建/交互成功率、评论遗漏、冲突恢复和总耗时。界面相似或协议测试通过都不足以得到这个结论。
