方法 / 身份与保留

一次局部修改，如何同时保留最新源码与用户仍在编辑的内容？

一张画面看起来已经更新，不代表旧草稿可以直接覆盖它。项目修订说明这份工程处于哪个状态，文件 hash 说明本次读取的具体文件是什么内容。先明确要改变的对象，再核对两种身份，才能把“修改成功”和“没有损伤别人的改动”一起说清楚。

    02 / 六节项目修订与文件 hash 回答不同问题。

    项目 revision 是整份工程的版本身份；文件 hash 是某个文件内容的身份。另一个人只改了样式文件，项目修订也可能变化；目标文件相同也不表示整批修改仍可按旧假设应用。两个检查都要使用本次读取的实际值。

    三种身份，三种作用

    revision
    项目修订
    sha256
    文件 hash
    sourceId
    源对象身份

    未应用提案、冲突草稿、失锚评论，需要分别保留身份与处理状态。

    03 / 六节冲突是一种有价值的拒绝。

    当旧值不再匹配，先保留用户草稿与原提案，再读当前文件并合并意图。只把 revision/hash 换新、原样重发旧内容，会把保护条件变成形式。拒绝应该说明哪一部分过期，以及怎样继续，而不是清空输入或报一个无法行动的错误码。

    返回目录 ↑

    04 / 六节评论应跟随语义对象。

    源码前增加一行文字不应把评论绑定到另一个元素。稳定标记用于追踪身份，偏移用于描述这一次源位置。标记被移除后，应明确失锚并回到文件层面核对，不能按旧 offset 猜测新对象。

    05 / 六节完成要分层报告。

    文件保存、编译、浏览器渲染、模型查看图像与实际交互是不同证据。编译成功不能证明按钮真的保存；截图产生也不能证明中文排版已经被看过。对尚未操作或没有条件检查的状态，应保留未验证说明。

    返回目录 ↑

    06 / 六节把改动交给下一个人。

    交付应保留入口、组件、样式、素材、版本和限制，让接手者可以继续编辑。单张图片不能替代源码包；源码包存在也不表示任意环境已具备所需运行条件。先核对包内文件，再说明如何验证和继续修改。

    给笔记保留清楚的身份

    revision  → 项目修订（示例 R7）
sha256    → 文件 hash（示例 H3）
sourceId  → 源对象身份

保留草稿 → 读取当前源码 → 协调意图 → 再校验
