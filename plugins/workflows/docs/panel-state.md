# Workflows 面板与状态草案

本文用于审阅面板和状态语义，尚未实现执行器、持久化、取消或产品界面。交互原型使用示例数据，不能作为真实 worker 或宿主集成的验证。已确认的产品约定以 [设计记录](design.md) 为准。

## 面板区域

| 区域 | 展示内容 |
| --- | --- |
| 概览 | 当前任务、脚本与计划预览、执行状态、动态任务计数，以及当前可用操作 |
| 任务 | 运行时已发现的任务、依赖和 worker；可以选中任务查看结果、执行尝试和日志 |
| 差异 | 隔离工作区中的差异、测试结果和 worker 报告，以及改动应用状态 |
| 日志 | 调度、worker、停止、恢复和应用事件；按任务筛选，并标明示例数据或真实运行来源 |

开始前展示编排逻辑、输入、只读与写入范围、并发限制。动态任务数量可能在运行中增加，计划预览不能承诺已知最终任务数。已完成任务保留在任务列表，新分支追加到列表；恢复尝试关联原任务，避免被误读为新的业务任务。

## 三组独立状态

### 工作流执行状态

| 状态 | 含义 |
| --- | --- |
| 待开始 | 已生成计划和脚本，等待用户开始；未启动 worker |
| 运行中 | 脚本正在调度、等待或处理 worker 结果 |
| 正在停止 | 已停止新调度，正请求中断活跃 worker 并等待收尾 |
| 已停止 | 活跃 worker 已结束，进度已保存，等待用户恢复 |
| 执行失败 | 本次执行未成功完成；展示失败原因，不等于所有任务结果失效 |
| 执行完成 | 脚本已结束，全部 worker 已收尾，结果可统一审查 |

核心路径为“待开始 → 运行中 → 执行完成”和“运行中 → 正在停止 → 已停止 → 运行中”。“执行失败”也必须与活跃 worker 是否收尾的事实一致；单个 worker 失败不自动等于整个工作流失败，脚本可能处理失败、重试或进入其他分支。具体错误策略仍需设计。

执行状态不能代替改动应用状态。“执行完成 · 待审查”表示当前项目尚未应用改动。

### 任务与 worker 状态

任务是编排的逻辑单元，worker 是任务的一次代理执行尝试。恢复可以给原任务创建新的尝试，并保留之前的中断记录。

| 状态 | 含义 |
| --- | --- |
| 等待中 | 任务已被发现，等待依赖或并发名额；尚未启动 worker |
| 运行中 | worker 正在执行任务 |
| 正在停止 | 已向 worker 发出中断请求，尚未确认结束 |
| 已完成 | 本次任务取得了结果；是否可缓存还需满足缓存规则 |
| 已中断 | worker 已结束，但任务未完成；保留日志和工作区改动 |
| 执行失败 | 本次尝试失败，保留错误及已有产物 |

第一版只读 worker 可以并行，写入 worker 使用隔离工作区且同时最多 1 个。只读任务、写入任务和测试任务的分类必须按实际工具权限和执行环境确定，不能仅靠任务标题判断。

“复用结果”是已完成任务的结果来源标记，不单独创建新的 worker 状态或执行尝试。

权限等待的展示、任务依赖失败后的状态、脚本主动跳过任务、单个 worker 的停止或重试，尚未确定，不作为当前已确认的操作。

### 改动应用状态

| 状态 | 含义 |
| --- | --- |
| 尚未汇总 | 执行尚未完成；不能据此判断隔离工作区没有改动 |
| 无改动 | 执行结束后确认没有需要应用的改动 |
| 待审查 | 执行已完成，统一差异和验证结果等待用户确认 |
| 应用中 | 用户已点击应用，正在将审阅的改动应用到当前项目 |
| 已应用 | 改动已成功应用到当前项目；这不等于已提交或推送 |
| 冲突 | 应用无法安全完成，展示冲突并等待处理 |

第一版原型在执行结束后统一展示差异。是否额外允许查看运行中或已停止时的部分差异，仍可讨论；即使允许，也不开放“应用”。“应用中”不能因为窗口关闭就显示为“已应用”。应用失败、部分应用、冲突解决及重试方式仍需设计，不将所有错误统一假定为冲突。

## 操作允许条件

| 操作 | 允许条件与行为 |
| --- | --- |
| 预览计划与脚本 | 开始前展示完整版本；运行后仍可查看本次使用的版本 |
| 开始 | 待开始，用户已看到当前脚本、输入和计划；启动动态编排，不自动授权应用改动 |
| 停止 | 运行中；停止新调度并请求中断所有活跃 worker，进入正在停止 |
| 恢复／继续 | 已停止，保存记录与工作区可用，脚本和输入符合恢复规则；复用满足条件的结果，重新启动未完成任务 |
| 查看差异和日志 | 有相应产物即可查看；执行完成后统一展示审查材料 |
| 应用 | 执行完成且改动待审查，用户确认当前差异后点击；应用冲突的检查和事务边界待定 |

正在停止时不重复触发停止，也不提前开放恢复。正在应用时不再次触发应用。脚本或输入变化后应重新预览；具体缓存失效和恢复条件仍需补齐。失败后采用“重试”“恢复”还是重新开始，待错误与缓存契约确定后再定。

## 动态进度与关闭 App

进度展示已知事实，例如“已完成 6 · 运行中 4 · 等待中 3”，并单独展示复用结果、中断和失败数量。计数按逻辑任务统计，执行尝试次数另列；未知的后续分支不计入等待数。展示阶段名可以帮助理解当前工作，但不以未知最终任务数计算固定百分比。

正常关闭 App 的目标语义与停止相同：停止调度、中断 worker、保存进度，不继续后台执行。重新打开后用户手动恢复；待开始、执行完成和待审查等不在运行的阶段保持原状态，不自动开始或应用。已完成结果、日志和工作区改动保留，停止不回滚代码。

宿主如何通知关闭、异常退出时如何识别遗留 worker 和未完整保存的记录，以及应用过程中关闭 App 的处理，尚未验证或确定。不能仅凭面板原型承诺这些能力已经可用。
